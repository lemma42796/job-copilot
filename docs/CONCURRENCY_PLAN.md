# 事实边界

本文是**尚未实施**的改造方案,不描述当前系统事实。当前系统事实以 `docs/STATUS.md` 和代码为准。

本文中的**上游配额为实测值**(见下一节),**本地瓶颈数字与 token 用量为读代码推算**,未经压测。P8 完成前不得在任何对外材料中引用推算值。

# 上游配额:不是瓶颈

qwen3.6-flash 实测配额,**该模型独享,不与 rerank / embedding 共用**:

| 维度 | 数值 |
| --- | --- |
| TPM | 10,000,000 |
| RPM | 30,000 |

两者比值隐含"平均每请求 333 token"。本项目单次生成调用的实际用量约 **15,000 token**(`RERANK_TOP_K=10` 个片段 × `MAX_CHUNK_TOKENS=1000` 上限,加 prompt 与输出),是该假设的 45 倍。

因此:

| 维度 | 允许的调用速率 | 是否先撞 |
| --- | --- | --- |
| TPM | 约 667 次/分 | **是** |
| RPM | 30,000 次/分 | 否,富余 45 倍 |

按单次调用 30 秒估算,TPM 允许**约 333 个 LLM 调用同时在飞**。当前 `llm_max_concurrency` 默认值为 4,**余量约 83 倍**。

**结论:上游配额不是瓶颈,当前全部瓶颈在自身代码与本地资源。** RPM 在本项目的请求形态下永远撞不到,后续不再考虑该维度。

配额独享还意味着 `qwen3-rerank` 与 embedding 各有自己的配额池,不占用上述 10M。因此文本生成的并发上限可以按本节数字独立推算,无需为检索链路预留额度。

上一版本文声称"上游配额是不可突破的硬天花板"、"做不到高并发 LLM 推理",该判断已被实测推翻,相关结论全部作废。

# 与现有文档的冲突

`docs/TECH_DESIGN.md` 当前定义系统范围为"单用户、本地优先的求职准备工作台",并明确"当前不做多用户 SaaS"。

本方案改变这一定位为**多用户线上服务**。定位更新并入 P0 一起做,因为 P0 本身就是这次范围变更的实现。

# 目标重新定义

上游配额既然有 83 倍余量,唯一的硬约束就变成了**成本**:上游不会因为限流帮我们刹车,打多少收多少。

## 商业形态(已确定)

- **多用户线上服务**,用户注册后使用。
- **共用平台 API key**,用户不接触 key。全系统共享同一个配额池,本文的 333 并发上限是全系统合计值,不是每用户值。
- **用户预充值余额,按官方 API 价格实扣,余额耗尽即禁用。** 余额本身就是限流机制,不再单独设配额档位。
- 充值链路(支付、对账、发票)本阶段**只做模拟**,不实现真实支付。重点在并发改造。

因此目标是三条:

1. **接入层无压力** — 提交任务、查询进度这类在线接口不触碰 LLM,可承载高 QPS。
2. **处理层在成本预算内尽可能高的吞吐** — 不是"吃满配额"。满配额运行等于 6 亿 token/小时,而且这些成本要由用户余额承担,吃满配额意味着用户余额被瞬间清空。
3. **过载不雪崩** — 超出承载能力时排队或明确拒绝,不出现连锁超时和重试风暴。

# 现状瓶颈

按撞墙先后排序。除上游配额外,均为读码推算。

| 序号 | 瓶颈 | 依据 | 推算影响 |
| --- | --- | --- | --- |
| 1 | 数据库连接池默认值 | `infra/db.py` 仅设 `pool_pre_ping`,未设 `pool_size` | SQLAlchemy 默认 5 + overflow 10 = 15;四个 SSE 接口全程持有 session,约 15 个并发会话打满 |
| 2 | 进程内并发闸门 | `llm/client.py` 经 `llm/admission.py` 注入 `asyncio.Semaphore`,默认 `JOBCOPILOT_LLM_MAX_CONCURRENCY=4` | 同时仅 4 个 LLM 调用在飞,相对上游余量低 83 倍 |
| 3 | 无用户体系 | `models/` 无 user 表,业务表无 `user_id` 列,无认证 | 多用户会读写同一份数据;按用户扣费与限流均无法实现 |
| 3b | 无余额与扣费 | 全仓无余额表;rerank 与 embedding 的成本已算出但未落 `llm_calls` | 上游有 83 倍余量,不会限流兜底;并发一放开即账单裸奔 |
| 4 | 无限流与熔断 | 全仓无 ratelimit / circuit breaker 实现 | 过载时 `llm/client.py` 的 tenacity 重试放大压力 |
| 5 | 单进程 uvicorn | `docker/api.Dockerfile` CMD 无 `--workers` | 仅使用单核 |
| 6 | worker 在 API 进程内 | `main.py` lifespan 中 `asyncio.create_task(embed_worker.run_forever)` | 见下条,是横向扩展的直接阻碍 |
| 7 | embed worker 查询无行锁 | `workers/embed_worker.py` 的 `SELECT ... WHERE embedding IS NULL LIMIT 10` 无 `FOR UPDATE SKIP LOCKED` | 多副本会取到同一批 chunk,重复调用 embedding 接口重复计费 |

## 上一版遗漏、本版补入的事实

- **需要异步化的 SSE 接口有四个,不是一个**:`POST /v1/quiz/sessions`(出题)、`POST .../answers/{i}/turns`(答题回合)、`POST /sessions/{id}/finish`(总结)、`POST /sessions/{id}/submit`(评分)。用户一场面试要走后三个十几次,只改出题接口不解决连接池占用。
- **rerank 完全绕过并发闸门**:`services/reranker.py` 自建 `httpx.AsyncClient` 直接请求上游,不经过 `llm/client.py`,不受 `llm_max_concurrency` 约束。由于 rerank 有独立配额池、不占用文本生成的 10M TPM,这不构成即时风险;但它同时意味着 rerank 侧完全没有并发与成本控制,P1 的用量上限需要单独覆盖这条链路。
- **单次答案提交最多触发 14 次 LLM 调用**:`agents/answer_judge/agent.py` 的 `MAX_JUDGE_ROUNDS = TOOL_MAX_CALLS * 2 + 4 = 14`,是 tool-calling 循环。闸门在循环体内逐次获取释放,不是整个 judge 占一个名额。按"一次提交一次调用"估算会严重低估用量。

## 已做对、无需改动的部分

- `profile_chunks` 与 `note_chunks` 的 HNSW 与 GIN 索引已建(migration `0005`、`0016`),检索层不是瓶颈。
- 响应缓存默认开启(`llm_cache_enabled`),dogfood 命中率 70%+,实际打到上游的调用约为总量三成。
- 评分逻辑在 Python 侧(`agents/answer_judge/scoring.py`),不占 LLM 调用,与并发无关。

# 分阶段方案

编号相对上一版已重排。核心变化:新增 P0(用户体系与数据隔离),它是多用户定位的前提;原"成本刹车"改为按用户余额实扣;原 Redis 全局闸门因上游余量充足推迟,移入附录。

## P0:用户体系与数据隔离

**目标**
让系统具备"用户"这个概念。这是多用户定位的前提,不做它,后续所有并发指标都没有意义 — 多个用户会读写同一份数据。

**依赖**
无。其余所有阶段的前置条件。

**现状**
`models/` 下 17 个模型无 user 表;笔记、quiz_session、jd、resume 等业务表**均无 `user_id` / `owner_id` 列**;无登录与身份识别;`settings.notes_fs_root` 为单一根目录,笔记文件不按用户分。全仓唯一的 `user_id` 是 `models/llm_call.py` 的可空审计字段,无对应用户表。

**改动点**
- 新增 user 表与认证(注册、登录、会话)。
- 所有业务表增加 `user_id` 列与索引,补 Alembic migration。
- 所有 service 层查询增加归属过滤。**这是本阶段风险最高的部分:漏一处即数据泄露,没有中间状态。**
- 笔记文件存储路径按用户分目录。
- 前端接入登录态。
- 同步更新 `TECH_DESIGN.md` 系统范围章节为多用户线上服务。

**验收标准**
- 两个账号各自导入笔记、各自出题,互相看不到对方的任何数据。
- 全仓审计:所有涉及业务表的查询均带 `user_id` 过滤,无遗漏。
- `TECH_DESIGN.md` 与本文不再存在互相否定的表述。

## P1:余额账本与扣费闸门

**目标**
用户按官方 API 价格实扣余额,余额耗尽即禁用。余额同时承担成本控制与限流两个职责。

**依赖**
P0(需要 user_id 才能记账)。**P2 的前置条件,顺序不可颠倒** — 实测上游 TPM 余量约 83 倍,不会通过限流帮我们刹车,先放并发后加扣费等于账单裸奔。

**现有基础**
三条计费链路的成本**都已能计算**,缺的是统一落账:

| 链路 | 成本计算 | 是否落 `llm_calls` |
| --- | --- | --- |
| 文本生成 | `llm/pricing.py` `cost_for()` | 是,经 `llm/db_logger.py` |
| rerank | `services/reranker.py` `_rerank_cost()` | **否**,仅进 Langfuse |
| embedding | `llm/embedders.py` `embed_cost_for()` | **否**,代码注释明示 S8 阶段未接 |

`models/llm_call.py` 已有可空 `user_id` 字段,是现成挂载点。缓存命中时 `cost_cny` 归零(`llm/client.py`),用户天然受益于缓存。

**改动点**
- 新增余额表与流水表。充值接口**做模拟实现**(直接改余额),不接支付。
- rerank 与 embedding 两条链路接入 `llm_calls` 记账,`user_id` 全链路透传。
- 调用前检查余额,调用后按 `cost_cny` 实扣。
- 余额耗尽后禁用:拒绝新任务,返回可读原因与当前余额。

**必须处理的三个设计问题**
1. **成本后验**:token 用量只有调用返回后才知道,无法精确预授权。做法是**每次调用前检查余额,调用后按实际扣**,允许小额透支。不做任务级预授权。
2. **任务中途耗尽产生半成品,这是接受的行为**:一场面试含 13 次以上 LLM 调用(`MAX_JUDGE_ROUNDS = 14` 使单次答案提交最多 14 次)。余额在任务中途归零时**就地中止,保留已产生的结果**,不回滚、不预留、不做任务级预检查。用户得到的价值与已扣的费用对应。

   由此产生的要求:
   - job 需要一条独立的终态表示"余额耗尽中止",与执行失败区分开,前端据此提示充值而非报错。
   - 中途产物必须已落库、不被回滚。`services/interview_service.py` 的答题回合逐轮持久化,天然满足;`services/quiz_service.py` 是末尾一次性 INSERT 全部题目,中止发生在生成前则无产物、发生在生成后则完整,也不产生坏数据。
   - 透支上界因此收紧为**单次调用成本**,而非单任务成本。并发调用下上界为"该用户同时在飞的调用数 × 单次调用成本",量级可忽略,不需要额外的并发任务数限制来兜底。
3. **三条链路必须全部扣费**:尤其 rerank,它当前既不落账也不过并发闸门,是完全无管控的一条计费线。

**验收标准**
- 跑完一场完整面试后,用户余额减少量与 `llm_calls` 中该用户的 `cost_cny` 合计一致,且覆盖生成、rerank、embedding 三条链路。
- 余额置零后,新任务被明确拒绝并返回当前余额。
- 面试进行到一半时把余额置零,任务就地中止且已产生的题目 / 答案 / 评分全部保留,job 终态为"余额耗尽中止"而非失败;透支不超过单次调用成本。
- 缓存命中的调用不扣费。
- 成本可按用户、按功能两个维度查询,与改造前的成本归因能力一致。

## P2:并发参数与连接池调整

**目标**
用最小改动量把同时在线用户数从个位数提升到二三十。

**依赖**
P1。

**改动点**
- `JOBCOPILOT_LLM_MAX_CONCURRENCY` 由 4 调整为 32(环境变量,不改代码)。
- `infra/db.py` 显式配置 `pool_size=20`、`max_overflow=20`。
- 确认 PostgreSQL `max_connections`(默认 100)对单进程 40 条连接有余量。

**为什么是 32 而不是 333**
此阶段四个 SSE 接口仍全程持有数据库 session,并发上限由连接池而非上游决定。LLM 并发设得再高也无法转化为实际吞吐。该值在 P3 完成后重新评估。

**验收标准**
- 并发会话数达到 25 以上时无 `QueuePool limit` 错误,无 `too many connections` 错误。
- 成本随并发上升如实计入各用户余额,无漏记。

## P3:长任务从在线请求中剥离

**目标**
在线接口不再承载 LLM 全流程,SSE 仅用于订阅进度,断线可重连续看。

**依赖**
P0。

**改动点**
- 四个 SSE 接口全部改造,不只出题接口:
  - `routers/quiz.py` `POST /sessions` — 出题
  - `routers/quiz.py` `POST .../answers/{i}/turns` — 答题回合(调用最频繁)
  - `routers/quiz.py` `POST /sessions/{id}/finish` — 结束总结
  - `routers/quiz.py` `POST /sessions/{id}/submit` — 提交评分
  - `routers/jd.py` 的对应长任务接口
- 上述 `POST` 改为落库建 job 后立即返回 202 与 job_id,不触碰 LLM。
- 新增只读的进度订阅接口,SSE 只推进度事件,支持从中间接入。
- `services/quiz_service.py`、`services/interview_service.py`、`services/jd_service.py`:生成器逻辑迁移到 worker 侧执行,进度由 `yield` 事件改为写入 job 事件表。
- 新增 job 与 job event 数据模型及 Alembic migration,job 表带 `user_id`。

**设计参考**
Paper Copilot 仓库已实现同形态模型(Job / Attempt / 事件订阅 / 断点恢复),直接复用其状态机设计,不重新设计。

**验收标准**
- 四个 `POST` 的 P99 响应时间均低于 200ms,且调用期间无 LLM 请求发出。
- 客户端在任务执行中断开 SSE 后重连,能收到断开期间产生的事件,任务不中断。
- 单个在线请求持有数据库 session 的时间不超过单次查询时长。
- 完成后重新评估 P2 中的 `llm_max_concurrency` 与 `pool_size`,连接池不再是并发上限。

## P4:拆出独立 worker 与真队列

**目标**
任务处理能力可通过增加 worker 副本线性扩展。

**依赖**
P3。

**改动点**
- `main.py`:移除 lifespan 中的 embed_worker 启动逻辑。
- 新增独立 worker 入口与 `docker/worker.Dockerfile`,`docker-compose.yml` 新增 worker 服务并支持副本数配置。
- 队列选型 Redis Streams:需要 consumer group、ack 与 pending 列表,消费者崩溃后任务可被接管。备选 pgmq(compose 注释中的 M2 原计划),但会让 PostgreSQL 同时承担业务库与队列两个角色,高负载下压力集中。
- 任务幂等:以 job_id 为去重键,worker 重启后重复消费不得重复调用 LLM 或重复扣费。
- `workers/embed_worker.py` 的 chunk 领取查询补 `FOR UPDATE SKIP LOCKED`,否则多副本重复计费。

**注意**
本阶段引入 Redis,`docker-compose.yml` 服务数将突破 README 与 AGENTS.md 中记录的"6 服务"约束,需同步更新那两处。

**验收标准**
- worker 副本从 1 增至 N,任务吞吐近似线性提升。
- 强杀一个 worker 进程,其未 ack 的任务被其他副本接管完成,无任务丢失、无重复扣费。
- 多副本同时运行 embed worker,同一批 chunk 只被 embedding 一次、只扣一次费。
- API 容器不再包含任何后台常驻任务。

## P5:多进程

**目标**
吃满多核。

**依赖**
P4(否则多进程会重复消费队列、重复扣费)。

**改动点**
- `docker/api.Dockerfile`:改为 `gunicorn -k uvicorn.workers.UvicornWorker -w N`。
- 重新校验总连接数:`API 进程数 × (pool_size + max_overflow) + worker 副本数 × 池大小` 必须小于 PostgreSQL `max_connections`。超出则引入 PgBouncer 做连接复用。

**验收标准**
- 压测中无 `QueuePool limit` 或 `too many connections` 错误。
- CPU 利用率随进程数增加而提升,不再单核饱和。

## P6:减少上游调用

**目标**
每省一次调用都是用户余额的净节省。在上游余量充足的前提下,本阶段的收益是省钱而非提吞吐。

**依赖**
无强依赖,可与 P5 并行。

**改动点**
- 语义缓存:`llm/cache_key.py` 当前为精确哈希,增加基于 embedding 相似度的近似命中路径,复用现有 embedding 链路。需要保留 `llm_response_cache` 表的成本审计能力,不得因改造丢失成本归因。
- 跳过不必要的调用:短 query 跳过 rewrite;候选集小于 top_k 时跳过 rerank。
- 收敛 judge 轮次:`MAX_JUDGE_ROUNDS = 14` 是单次答案提交的调用数上界,评估实际分布后下调。
- 批处理:`workers/embed_worker.py` 当前一轮一 batch、上限 10(对齐百炼 EMBED_BATCH_LIMIT),队列积压时改为一轮并发多 batch。

**注意**
跨用户共享缓存需要单独判断。同一 query 命中另一用户产生的缓存会带来两个问题:一是笔记内容属于不同用户,存在泄露风险;二是计费归属不清。默认应按用户隔离缓存,除非能证明缓存内容不含用户私有数据。

**验收标准**
- 相同压测负载下,发往上游的调用次数与 token 消耗较改造前下降,且出题质量评测指标不下降。
- 成本归因能力保持可用。
- 缓存不跨用户泄露笔记内容。

## P7:过载保护

**目标**
超出承载能力时行为可预期,不雪崩。

**依赖**
P4(Redis)。P1 已覆盖成本维度,本阶段补容量维度。

**改动点**
- 队列水位:超过阈值直接返回 503 与 `Retry-After`,不允许队列无限增长。
- 熔断:上游连续返回 429 时短暂停止发送。当前 `llm/client.py` 的 tenacity 重试在过载时会放大压力,必须有熔断兜底。
- 任务 deadline:超期任务直接判死并释放 worker,已消耗部分照常扣费。

**验收标准**
- 以 10 倍于承载能力的负载压测,系统返回明确的 429 / 503,不出现连锁超时,已入队任务仍能正常完成。
- 人为使上游持续返回 429,熔断在阈值内触发,恢复后自动放行。

## P8:压测与基线

**目标**
用实测数字替换本文所有推算值。

**依赖**
P0 到 P7。

**改动点**
- 引入 k6 或 locust,脚本纳入仓库。
- 分两组指标:在线接口(提交、查进度)的 QPS 与 P99;端到端任务完成率、排队时长与吞吐。

# 附录:已推迟的阶段

## 全局并发闸门改为 Redis 实现

**推迟理由**
原设计目的是"多进程多副本下不超上游配额"。按实测配额重算:上游允许约 333 个并发调用,即便 8 个 API 进程各自持有 32 的进程内闸门,合计 256 仍在余量内。在扩展到 10 个以上进程之前,该阶段不产生实际收益,而其复杂度(Redis 依赖、Lua 原子脚本、TPM 与 QPS 双维度计数)是实打实的。

**触发条件**
API 进程数与 worker 副本数合计使 `进程数 × llm_max_concurrency` 接近 333 时启动。

**届时的改动点**
- Redis 令牌桶,Lua 脚本保证原子性。
- 通过 `llm/client.py` 已预留的 `concurrency_gate_factory` 注入,`LLMClient` 接口不变。
- 必须双维度限制 QPS 与 TPM。
- 必须同时接管 `services/reranker.py`,它当前自建 httpx client 绕过闸门。

# 预期结果

- 在线接入层:可承载高 QPS,因其只读写数据库与队列。
- 任务处理吞吐:受成本预算约束,而非上游配额约束。
- 用户体验:从"等待数十秒或超时"变为"立即返回 + 进度可见 + 断线可续"。
- 过载行为:排队或明确拒绝,不雪崩。

# 风险

- **数据泄露**:P0 要给十几张业务表补 `user_id` 并给所有查询加过滤,漏一处即一个用户能读到另一个用户的笔记与面试记录。这类改动没有中间状态,必须全仓审计。是本方案风险最高的一项。
- **成本失控**:上游有 83 倍余量,不会通过限流帮我们刹车,余额扣费是唯一的刹车。P1 必须先于 P2 落地,顺序不可颠倒。注意扣费有三条独立链路,rerank 当前既不落账也不过并发闸门。
- **范围膨胀**:P3 与 P4 触及核心数据流,且 P3 的范围是四个 SSE 接口而非一个。改造期间产品功能可能不稳定,建议在独立分支进行,合并前跑通现有全部单测与评测集。
- **估算失真**:本文的并发上限建立在"单次调用约 15,000 token、耗时约 30 秒"这两个估算上。任何一个偏离一个数量级,结论都要重算。P9 之前该数字只用于内部决策。
- **文档漂移**:本方案会使 `TECH_DESIGN.md` 的系统范围、README 与 AGENTS.md 的服务数约束失效,每阶段完成后同步更新。
