# M2.1 失败回退与工具错误分类

## 目的

M2.1 的 Agentic RAG 要面对失败:

- 检索 0 命中。
- reranker 失败。
- LLM schema invalid。
- Judge 超时。
- SSE 断线。
- 数据库写入冲突。
- 用户 abandon。

这篇补失败分类和回退策略,避免 Agent 只在 happy path 上好看。

## 错误分类

建议分层:

```text
user_error
retrieval_empty
tool_transient
tool_permanent
schema_invalid
policy_boundary
state_conflict
provider_rate_limited
provider_timeout
storage_error
client_disconnected
```

错误类型决定:

- 是否重试。
- 是否降级。
- 是否提示用户。
- 是否写入失败状态。
- 是否进入人工可排查日志。

## 0 命中

M2 已锁定:

```text
命中 chunks < 3 起步直接报"笔记里没这主题"
```

M2.1 不能因为 Agent 化就绕过这个边界。追问时如果当前主题证据不足,应:

- 明确说明笔记证据不足。
- 请求用户换主题或补笔记。
- 不编造题目或评分依据。

## Reranker 失败

可能原因:

- provider timeout。
- 429。
- schema/response parse error。
- 网络代理问题。

回退策略取决于质量要求:

- 对出题链路,可以考虑 lexical/vector RRF 结果降级,但要标记 `rerank_degraded`。
- 对高风险评分 evidence,宁可中止也不要用低可信 context。

M2 当前 reranker 无本地 fallback,所以实现时要尊重已锁定决策。

## LLM schema invalid

结构化输出失败:

- JSON parse error。
- 缺字段。
- enum 非法。
- evidence ids 不存在。
- 分数超范围。

处理:

1. 记录原始输出摘要。
2. 可做一次 repair prompt 或 retry。
3. 仍失败则标记 agent_failed。
4. 不把 invalid 输出写成正式结果。

不要让前端自己猜字段。

## Provider timeout

Provider timeout 可重试,但要:

- 限次数。
- 指数退避。
- jitter。
- 总 deadline。
- idempotency key。

用户等待的 SSE 中,可以推送:

```text
judge_retrying
```

但最终状态必须落库。重试次数耗尽后,session 应进入可恢复失败状态,允许用户重试或 abandon。

## 429 Rate Limit

429 要解析 retry-after。后台任务可以延迟重试,用户等待路径要给出明确状态。

优先级:

1. 用户正在等待的 submit/judge。
2. session 恢复必要任务。
3. embedding。
4. eval batch。

eval batch 不能抢光 provider quota。

## State conflict

状态冲突例子:

- 用户 abandon 时 Judge 正在写回。
- 多标签页重复 submit。
- 刷新后旧 SSE 继续推事件。
- worker lease 过期后两个 worker 并发。

解决:

- 条件更新。
- version/fencing token。
- 幂等 key。
- 状态机白名单。

例如:

```sql
update judge_runs
set status = 'succeeded'
where id = :id and status = 'running' and run_token = :token;
```

## Client disconnected

SSE 断开不等于业务失败。

策略:

- 如果任务短且重要,可继续完成并落库。
- 如果任务昂贵且可取消,检查取消信号。
- 无论如何,写回时要检查 session 状态。

前端重连后查 DB 当前状态,不要要求后端补所有 SSE token。

## Storage error

DB 写失败比 LLM 失败更敏感。因为结果可能已经生成但没保存。

处理:

- 不告诉用户 completed。
- 记录可重试失败。
- 若有原始结果临时保存,要注意隐私和过期。
- 下次重试可能需要重新 Judge。

不要只把错误吞掉后继续推 completed event。

## 错误展示

用户文案要区分:

- 主题没有笔记证据。
- 当前服务繁忙。
- 评分暂时失败,可重试。
- 会话已被放弃。
- 输入不合法。

不要把所有错误都说成"网络错误"。

## 可观测字段

记录:

- session_id。
- question_id。
- run_id。
- state_before/state_after。
- error_type。
- provider/model。
- prompt_version。
- retry_count。
- degraded flag。
- evidence_chunk_ids。

这些字段服务排查和评测。

## 面试追问

问: Agent 工具调用失败怎么处理?

答: 先分类错误。网络/5xx/429 可有限重试,输入非法/schema invalid 不应盲重试,检索 0 命中要边界返回,状态冲突要读当前状态并幂等响应。失败状态要落库,前端刷新可恢复。

问: SSE 断线是否要取消 Judge?

答: 不一定。SSE 只是通知通道。可以根据任务成本和用户意图决定是否取消,但最终写回必须检查 session 状态。用户刷新应从数据库恢复,不是依赖 SSE。

问: 为什么 invalid JSON 不能写入正式结果?

答: 因为下游 UI、评分汇总和追问决策依赖结构化字段。invalid 输出会污染状态机。应 retry/repair,失败则进入明确失败状态。

## Hard negatives

- 0 命中不能让 Agent 自己编。
- 429 不是 schema 错误,处理方式不同。
- SSE disconnected 不是业务 completed。
- retry 不是无限循环。
- degraded result 必须可观测,不能悄悄降级。
