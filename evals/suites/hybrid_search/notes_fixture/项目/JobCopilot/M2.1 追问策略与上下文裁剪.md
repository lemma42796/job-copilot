# M2.1 追问策略与上下文裁剪

## 目的

M2.1 的核心不是多 Agent 炫技,而是 `InterviewCoachAgent` 能在面试闭环里做出可解释的下一步:

```text
检索 -> 出题 -> 等答 -> 评分 -> 决策 -> 追问/总结
```

这篇专门补追问策略和多轮上下文裁剪,服务后续状态机实现与 RAG 评测。

## 追问不是随机加题

追问应该来自评分证据:

- 用户漏掉关键点。
- 用户答错了概念。
- 用户编造了不存在的内容。
- 用户回答太泛。
- 用户虽然答对,但缺少工程取舍。

追问目标要明确:

- 补概念。
- 查边界。
- 查落地。
- 查排障。
- 查取舍。

不要每题都无脑追问。达到质量阈值时可以总结进入下一题或结束。

## 追问输入

追问决策需要:

- 当前 question。
- user_answer。
- judge evidence。
- score breakdown。
- retrieval chunks。
- session history 摘要。
- already_asked_followups。
- max_followup_rounds。

不需要把完整历史每次都塞入 prompt。多轮越长,越要做上下文裁剪。

## 决策枚举

`decide_next_action` 可输出:

```text
followup
next_question
summarize
end
needs_more_context
```

M2.1 初版可以先保守:

- 分数低且 evidence 足够 -> followup。
- 分数中等且有明确缺口 -> followup。
- 分数高 -> summarize 或 next_question。
- 检索证据不足 -> needs_more_context 或 end with boundary。
- 追问轮次达到上限 -> summarize。

## 追问类型

概念纠偏:

```text
你刚才把 Context Cache 当成会话记忆。请解释两者边界。
```

工程落地:

```text
如果 submit SSE 断线,后端如何保证 Judge 结果可恢复?
```

边界条件:

```text
如果 reranker 返回空结果,出题链路应该继续还是中止?
```

取舍:

```text
为什么 M2.1 不先做多 Agent,而是状态机?
```

排障:

```text
Langfuse trace 没记录 generation,你会先查哪些点?
```

## fabricated 处理

如果 AnswerJudge 标记 fabricated:

- 不应温和放过。
- 可触发纠偏追问。
- 分数应锁顶或显著扣分。
- 追问要围绕证据边界。

例:

```text
你的回答提到 M2 已经支持岗位类 query,但当前锁定是 M3 才做三源融合。请说明主题类 query 和岗位类 query 的边界。
```

这是 JobCopilot 私有事实 hard negative 的关键价值。

## 上下文裁剪

多轮上下文不能无限增长。裁剪原则:

保留:

- 当前题。
- 最近一轮用户答案。
- 最近 judge evidence。
- 当前追问目标。
- 关键 session summary。
- 与当前追问直接相关 chunks。

压缩:

- 更早问答。
- 已掌握知识点。
- 重复 evidence。

丢弃:

- UI 进度事件。
- 与当前题无关 chunks。
- 已过期草稿。
- 完整 provider 原始响应。

## Session memory 与 Context Cache

Session memory:

- 应用侧语义记忆。
- 记录用户弱点、已问问题、已纠偏内容。
- 需要落 DB 或可恢复存储。

Context Cache:

- provider 侧公共前缀缓存。
- 只优化重复前缀计算/计费。
- 有 TTL。
- 不是业务记忆。

M2.1 多轮讨论可能重新评估是否打开显式 cache_control,但不能依赖它恢复状态。

## 状态恢复

刷新 `/quiz?session=4` 时,应恢复:

- session status。
- questions。
- answers/drafts。
- judge results。
- followup state。
- summary。

不应依赖:

- 前端内存。
- SSE 未读缓冲。
- provider cache。
- Agent scratchpad 临时变量。

状态机每一步要有可落库状态或可重建输入。

## 追问质量评测

可评测指标:

- branch_accuracy:下一步动作是否符合标注。
- followup_relevance:追问是否针对缺口。
- evidence_groundedness:是否基于证据。
- redundancy_rate:是否重复问过。
- unsafe_boundary_rate:是否越过笔记事实。
- recovery_success:中断后能否恢复。

不要只看追问文字是否流畅。

## Prompt 约束

追问 prompt 应明确:

- 不引入笔记外事实。
- 不把未来里程碑当已完成。
- 不重复已问追问。
- 输出结构化 JSON。
- 给出追问原因。
- 遇到证据不足要说边界。

结构化输出示例:

```json
{
  "action": "followup",
  "reason": "answer_confused_context_cache_with_session_memory",
  "followup_question": "...",
  "target_gap": "context_cache_boundary",
  "evidence_chunk_ids": [1, 2]
}
```

## 面试追问

问: M2.1 追问依据是什么?

答: 依据 AnswerJudge 的 evidence 和分项分数,不是随机生成。系统要识别漏点、错点、编造、泛泛而谈和缺少工程取舍,再决定追问、下一题或总结。

问: 多轮上下文如何裁剪?

答: 保留当前题、最近答案、judge evidence、追问目标、session summary 和相关 chunks。早期问答压缩成摘要,无关 chunks 和 UI 事件丢弃。业务状态必须落库,不能依赖 provider Context Cache。

问: 什么时候不追问?

答: 分数足够高、缺口不明确、证据不足、追问轮次达到上限或用户请求结束时,应总结或结束。无脑追问会降低体验。

## Hard negatives

- 追问不是随机换一道题。
- Context Cache 不是 session memory。
- Agent scratchpad 不是可恢复状态源。
- SSE event 不是业务状态。
- 多 Agent 数量不是 M2.1 高级感来源。
