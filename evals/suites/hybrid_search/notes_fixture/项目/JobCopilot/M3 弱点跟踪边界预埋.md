# M3 弱点跟踪边界预埋

## 为什么现在预埋 M3

当前阶段是 M2.1,不应提前实现 M3。但 dogfood 语料可以预埋 M3 弱点跟踪相关知识,用于后续 RAG 和追问评测。

预埋的目的:

- 让 M2.1 追问能区分 session 内缺漏和长期弱点。
- 给后续 M3 设计提供语料。
- 制造 M2.1/M3 边界 hard negatives。
- 避免把未来功能误答成当前已完成。

## 当前边界

当前事实:

- M2 已完成 RAG 出题、答题、Judge、session 恢复。
- M2.1 当前做 `InterviewCoachAgent` 状态机和追问分支。
- M3 才做弱点跟踪、SR、岗位类三源出题、简历诊断。

因此,任何回答都要区分:

```text
M2.1 = session 内追问和恢复
M3 = 长期弱点跟踪和岗位类三源融合
```

## 弱点是什么

弱点不是单次低分。更稳的定义:

```text
在多个题目、多个 session 或多个时间点中反复出现的可归因能力缺口。
```

例:

- 总是漏掉边界条件。
- 只背概念,不会结合项目。
- 对事务和异步边界理解弱。
- RAG 0 命中时倾向编造。
- 讲 Redis 时忽略持久化和一致性。

单次回答差可能是题目难、表达失误或 evidence 不足,不能直接写成长期弱点。

## 弱点维度

可以按维度:

| 维度 | 例子 |
|---|---|
| concept | 概念不清 |
| tradeoff | 取舍不足 |
| implementation | 落地细节弱 |
| failure_mode | 故障处理弱 |
| evidence_grounding | 不基于证据 |
| project_mapping | 不能映射到 JobCopilot |
| communication | 表达结构差 |

AnswerJudge 的分项 evidence 可以成为弱点候选,但不能自动等同长期弱点。

## 弱点证据

弱点记录应包含:

- question id。
- session id。
- answer excerpt。
- judge evidence。
- missing point。
- score dimension。
- source chunk ids。
- timestamp。
- confidence。

不要只存:

```text
用户不懂 Redis
```

这种标签太粗,不可追踪。

更好:

```text
用户在 Redis 限流题中只提到固定窗口计数器,漏掉 token-aware limit 和 provider TPM。
```

## 从 M2.1 到 M3

M2.1 可以生成 session 内 gap:

```text
missing_points = ["没有说明 token bucket 为什么适合 TPM", "没有区分 Redis cache 和 Context Cache"]
```

M3 才把多个 gap 聚合成长期 weakness:

```text
weakness = "LLM 应用成本/限流建模不足"
```

不要在 M2.1 第一刀就实现复杂长期画像。

## Spaced Repetition

SR 不是简单"错题再问一次"。它需要:

- 复习间隔。
- 掌握度。
- 遗忘曲线。
- 题目变体。
- 弱点标签。
- 用户负担控制。

M3 可以把弱点转成复习计划:

- 今天:修正概念。
- 下次:换场景迁移。
- 后续:综合系统设计题。

但当前 dogfood 只预埋,不实现。

## 岗位类三源融合

M3 岗位类 query 要融合:

1. 笔记 RAG。
2. 全库单条简历。
3. 用户选定 JD 子集职责/要求。

这和 M2 主题类 query 不同。M2 不能提前把岗位类降级成普通主题 query。

弱点跟踪也要考虑岗位上下文:

- 后端岗位关注事务、并发、系统设计。
- AI 应用岗位关注 RAG、评测、prompt、可观测。
- 全栈岗位关注前端状态和 API 契约。

## 简历单条记录

锁定决策:

```text
简历全库单条记录,不做简历库/多份切换。
```

M3 简历诊断基于那一份简历。不要设计多简历版本库作为当前事实。

Hard negative:

```text
候选人可以上传多份简历,系统按岗位切换版本。
```

这可能是通用产品建议,但不是 JobCopilot 当前决策。

## 弱点和隐私

弱点画像涉及用户能力评价,需要谨慎:

- 不要写侮辱性标签。
- 不要过度推断。
- 给出证据和可改进建议。
- 允许用户查看和修正。
- 避免把敏感简历内容写入不必要日志。

Langfuse trace 和日志需要 redaction 策略。

## 弱点置信度

弱点应有 confidence:

- low:单次 evidence。
- medium:同类题多次出现。
- high:跨 session 反复出现。

例:

```json
{
  "weakness": "事务边界与外部调用",
  "confidence": "medium",
  "evidence_count": 3
}
```

不要一次答错就 high confidence。

## 弱点合并

多个 gap 可能属于同一弱点:

- "不知道 @Async 不继承事务"。
- "在事务里调用 LLM"。
- "没有 afterCommit/outbox 概念"。

可合并为:

```text
异步任务与事务边界理解不足
```

合并需要 taxonomy,否则标签会爆炸。

## 弱点拆分

过粗标签要拆:

```text
数据库不好
```

拆为:

- 索引选择。
- 事务隔离。
- 锁等待。
- SQL 执行计划。
- JSONB schema 边界。

这样复习才可执行。

## 题目变体

弱点复习不能只重复原题。应生成变体:

- 概念题。
- 场景题。
- 故障排查题。
- 项目映射题。
- 反例纠错题。

例:

原弱点:只按 QPS 限流。

变体:

```text
如果 AnswerJudge 的 input tokens 是 query rewrite 的 60 倍,限流器如何估算成本?
```

## 进步判断

不要只看单次分数。可以看:

- 同类题平均分上升。
- missing point 减少。
- fabricated 减少。
- 能主动提 tradeoff。
- 能映射到 JobCopilot。

M3 可以给用户展示弱点趋势,但要避免过度仪表盘化。

## 和 RAG 评测关系

弱点跟踪依赖 RAG 质量。如果检索给错 evidence,Judge 可能误判用户弱点。

所以 M2 RAG 补测必须先做:

- recall。
- precision。
- zero-hit。
- unsafe boundary。
- hard negatives。

弱点系统不能建立在脏 evidence 上。

## 和 AnswerJudge 关系

AnswerJudge 输出应包含可聚合字段:

- missing_points。
- misconception。
- evidence verdict。
- dimension scores。
- suggested_followups。

但总分权重仍由 Python 控制。弱点聚合也不应让 LLM 单独决定最终画像。

## 和 InterviewCoachAgent 关系

M2.1 的 `InterviewCoachAgent` 可以在 session 内使用短期记忆:

- 本题漏点。
- 上一轮追问。
- 当前主题掌握情况。

M3 再做长期 memory:

- 跨 session 弱点。
- SR 计划。
- JD 匹配弱点。
- 简历诊断建议。

不要把两者混成同一个 memory。

## 数据模型预想

可能实体:

- weakness_observations。
- weakness_clusters。
- review_items。
- review_attempts。

观察记录不可轻易覆盖。聚合结果可以重算。

```text
observation = 原始证据
cluster = 聚合解释
review_item = 复习任务
```

## API 预想

未来可能:

- `GET /weaknesses`
- `GET /weaknesses/{id}`
- `POST /review-items/{id}/attempts`
- `GET /review-plan`

但当前 M2.1 不实现这些。只是预埋语料。

## UI 预想

M3 UI 应:

- 展示弱点证据。
- 展示建议复习。
- 支持跳回原题。
- 区分低/中/高置信度。
- 避免羞辱式文案。

不应:

- 用红色大字给用户贴标签。
- 把一次失误当人格判断。
- 隐藏 evidence。

## Hard negatives

错误说法:

- M2.1 已经实现长期弱点跟踪。
- 弱点就是单次低分。
- M3 会支持多份简历库。
- 岗位类 query 在 M2 已经完成。
- LLM 可以单独决定用户长期弱点。

正确说法:

- M2.1 做 session 内追问和恢复。
- M3 做长期弱点和 SR。
- 简历是全库单条记录。
- 岗位类 query 必须三源融合。
- 弱点要基于多次 evidence 聚合。

## 面试追问

### 如何避免误判用户弱点?

需要多次证据、明确 missing point、RAG evidence 可靠、置信度分级,并允许用户复习后更新掌握度。

### 为什么弱点不能只看总分?

总分太粗。两个同分答案可能一个概念错,一个缺实现细节。弱点需要维度和 evidence。

### 弱点跟踪和错题本区别?

错题本记录题目。弱点跟踪抽象能力缺口,并能生成变体和复习计划。
