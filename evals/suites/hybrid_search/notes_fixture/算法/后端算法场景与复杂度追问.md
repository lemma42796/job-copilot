# 后端算法场景与复杂度追问

## 目的

这篇笔记把常见算法和真实后端问题连接起来。面试官经常不直接问"写一个堆排序",而是问:

```text
如何从一百万条候选里取 Top 100?
如何做滑动窗口限流?
如何判断任务依赖是否有环?
如何给搜索结果去重并保持稳定排序?
```

回答要能从业务约束落到数据结构和复杂度。

## Top-K

问题:

```text
有 n 个候选结果,每个有 score,取前 k 个。
```

方案:

- 全量排序:`O(n log n)`。
- 小根堆维护 k 个元素:`O(n log k)`。
- quickselect 平均 `O(n)`,但结果内部还需排序。

工程取舍:

- n 小时直接排序,代码简单。
- n 很大且 k 小时用堆。
- 要分页时不能只做 top-k,还要考虑稳定 cursor。

RAG pipeline 中 candidate 数通常不大,排序更容易审计。过早优化 top-k 反而可能让排序稳定性变差。

## 稳定排序与可复现

搜索系统常见排序键:

1. reranker score desc。
2. RRF score desc。
3. source priority desc。
4. note updated_at desc。
5. chunk_id asc。

最后一个稳定 tie-breaker 很重要。否则同样输入可能每次返回不同 chunks,导致:

- 评测报告不可复现。
- Judge evidence 波动。
- 用户刷新后题目上下文变化。

## 去重

常见去重 key:

- `chunk_id`。
- `note_id + heading_path`。
- `content_hash`。
- `canonical_url`。
- `question_hash + answer_hash`。

去重的复杂度通常是 `O(n)` HashSet。

但去重粒度要谨慎:

- 按 chunk 去重太细,近重复段落还会重复。
- 按 note 去重太粗,同一 note 多个不同章节会被误删。
- 按 content_hash 去重只能处理完全相同文本。

JobCopilot 的 parent-doc 扩展阶段要避免同一个 parent doc 下多个 chunk 把 final context 挤满。

## 滑动窗口

滑动窗口适合连续区间问题:

- 最长无重复子串。
- 固定窗口统计。
- 最近 N 秒请求数。
- stream token 速率统计。

限流里的滑动窗口可以用:

- Redis sorted set 保存 timestamp。
- 环形数组保存桶计数。
- 本地内存窗口,适合单实例近似。

复杂度:

- sorted set 插入删除 `O(log n)`。
- 环形桶通常 `O(1)`。

面试要说明分布式场景下本地窗口不准确,需要 Redis 或网关统一计数。

## 令牌桶和漏桶

令牌桶:

- 按速率生成 token。
- 请求消耗 token。
- 允许一定突发。

漏桶:

- 请求进入桶。
- 按固定速率流出。
- 更平滑,突发被排队或丢弃。

LLM provider rate limit 通常需要:

- 每分钟请求数。
- 每分钟 token 数。
- 并发请求数。
- retry-after 解析。

不要只说"加 Redis 限流",要说明限的是哪种资源。

## LRU 实现

LRU = HashMap + 双向链表。

操作:

- get:HashMap 找节点,移到链表头。
- put:存在则更新并移头;不存在则插入头;超容量删尾。

复杂度 `O(1)`。

后端常见追问:

- 并发下如何加锁。
- TTL 和 LRU 如何组合。
- 缓存值很大时如何控制内存。
- 热 key 如何处理。

LLM 应用中,embedding cache 可用 LRU,但 judge result 缓存更依赖版本化 key。

## 布隆过滤器

布隆过滤器可以回答:

```text
这个 key 一定不存在,或者可能存在。
```

适合:

- 防缓存穿透。
- 快速过滤不存在 ID。
- 大规模集合 membership 近似判断。

不适合:

- 权限判断。
- 金融扣款。
- Judge fabricated 判定。

因为有假阳性。假阳性在缓存穿透里可接受,在权限里不可接受。

## 一致性哈希

一致性哈希用于节点扩缩容时减少 key 迁移。

核心:

- hash ring。
- 虚拟节点。
- key 顺时针找到节点。

场景:

- 分布式缓存。
- 分片存储。
- provider key 池分配。

面试陷阱:

- 一致性哈希不保证强一致性。
- 它解决的是分片映射变更成本,不是数据复制协议。

## 跳表

跳表用多层有序链表实现近似 `O(log n)` 查找。

Redis sorted set 使用跳表加 hash table 的组合。

适合回答:

- 排行榜。
- 延迟队列。
- 范围查询。

任务调度中可用 sorted set 按 `next_run_at` 排序,取到期任务。但如果需要事务和复杂状态,Postgres jobs 表会更容易保证一致性。

## 堆与延迟队列

延迟队列可以用小根堆按执行时间排序:

```text
heap top 是最早 next_run_at
如果 top 到期,弹出执行
否则 sleep 到 top 时间
```

分布式场景要额外处理:

- worker 抢占。
- clock skew。
- 任务持久化。
- 失败重试。
- 幂等。

只在内存里放 heap,进程重启任务会丢。面试时要主动区分内存调度器和持久化任务系统。

## 环形缓冲区

环形缓冲区适合固定容量队列或滑动统计。

特点:

- 空间固定。
- 读写指针循环。
- 避免频繁分配。

场景:

- 日志 buffer。
- streaming 事件缓存。
- 最近 N 次请求统计。

SSE 断线恢复不能只靠内存环形缓冲区。JobCopilot session 恢复应以数据库状态为准,而不是期望浏览器能补齐所有事件。

## 字典树与倒排索引

Trie 适合前缀匹配,倒排索引适合全文检索。

文档搜索常用倒排索引:

```text
term -> posting list(doc_id, positions, tf)
```

BM25 基于词频、文档频率和文档长度归一。

RAG hybrid search 同时用 lexical 和 vector,不是 Trie 能解决的问题。

## 复杂度表达模板

回答复杂度时可以这样说:

```text
设 n 为候选 chunk 数,k 为最终保留数量。
如果全量排序是 O(n log n),如果用大小为 k 的堆是 O(n log k)。
当前业务 n 由 top lexical + top vector 限制在几百以内,直接排序更简单且便于调试。
```

这比只说"优化到 O(n log k)"更像工程回答。

## 面试追问

问: 如何从 RAG 候选 chunk 中选 final context?

答: 先按 reranker score 和 RRF score 排序,再做 parent doc 扩展和去重。选择时要考虑 token budget、来源覆盖和 evidence provenance。复杂度通常候选数有限,直接排序即可;更重要的是稳定 tie-breaker 和可审计。

问: 如何做 provider rate limit?

答: 先定义限流维度:请求数、token 数、并发数、用户级还是全局级。单实例可本地令牌桶,多实例要用 Redis 或网关。遇到 429 应解析 retry-after,退避重试,并把 eval batch 和用户等待请求分优先级。

问: LRU cache 为什么要 HashMap + 双向链表?

答: HashMap 保证按 key O(1) 定位节点,双向链表保证 O(1) 移动到头部和删除尾部。单独 HashMap 无法知道最近最少使用顺序,单独链表查找又是 O(n)。

## Hard negatives

- 令牌桶不是漏桶。令牌桶允许突发,漏桶更平滑。
- 布隆过滤器不是权限系统。它有假阳性。
- 一致性哈希不是强一致性协议。它只解决分片映射。
- Top-K 堆优化不是所有排序问题的最佳答案。分页和稳定排序可能更重要。
- 内存延迟队列不是可靠任务系统。进程重启会丢任务。
