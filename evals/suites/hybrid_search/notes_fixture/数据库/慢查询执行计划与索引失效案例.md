# 慢查询执行计划与索引失效案例

## 目的

后端面试经常问慢查询排查。优秀回答不只是"加索引",而是能说明:

- 如何定位慢 SQL。
- 如何看执行计划。
- 为什么索引失效。
- 如何平衡写入成本和查询性能。
- 如何避免深分页。

JobCopilot 里 notes、chunks、quiz_sessions、judge_results 都会产生查询。RAG 检索还涉及全文索引和向量索引,但基础 SQL 索引仍然重要。

## 慢查询排查步骤

通用步骤:

1. 从慢查询日志/APM 找 SQL。
2. 看调用频率和 P95/P99。
3. 用 `EXPLAIN` 看执行计划。
4. 检查过滤条件、排序、回表、扫描行数。
5. 看索引设计和统计信息。
6. 验证优化效果。

不要直接在生产盲目加索引。索引会影响写入和存储。

## 执行计划关注点

MySQL 常看:

- type。
- possible_keys。
- key。
- rows。
- Extra。

PostgreSQL 常看:

- Seq Scan。
- Index Scan。
- Bitmap Heap Scan。
- Nested Loop。
- Hash Join。
- Sort。
- actual time。
- rows。

要看估算行数和实际行数差距。差距大可能是统计信息不准或数据分布倾斜。

## 全表扫描

全表扫描不一定错。

小表全扫可能比走索引更快。错的是大表高频查询无条件或条件选择性差导致大量扫描。

例子:

```sql
select * from note_chunks where user_id = ? and note_id = ?;
```

适合索引:

```text
(user_id, note_id)
```

如果只建 `note_id`,多租户场景可能扫到其他用户数据,再过滤 user_id。

## 联合索引最左前缀

索引:

```text
(user_id, status, created_at)
```

可用于:

```sql
where user_id = ?
where user_id = ? and status = ?
where user_id = ? and status = ? order by created_at
```

不适合只按 `status` 查询。

设计联合索引时要结合:

- 等值条件。
- 范围条件。
- 排序。
- 选择性。
- 查询频率。

## 范围条件

联合索引中遇到范围条件后,后续列通常难以继续用于精确定位。

例:

```text
(user_id, created_at, status)
where user_id = ? and created_at > ? and status = ?
```

`status` 可能无法充分使用。若常按 status 过滤再按时间排序,索引顺序可能应是 `(user_id, status, created_at)`。

## 索引失效案例

常见:

- 对索引列使用函数。
- 隐式类型转换。
- like 前缀通配。
- OR 条件不当。
- 选择性太差。
- 统计信息过期。
- 排序方向不匹配。

例:

```sql
where date(created_at) = '2026-05-12'
```

可能无法利用 created_at 索引。改成范围:

```sql
where created_at >= '2026-05-12'
  and created_at < '2026-05-13'
```

## 回表与覆盖索引

二级索引找到主键后,再查主表叫回表。

覆盖索引是查询字段都在索引里,无需回表。

例:

```sql
select id, title
from notes
where user_id = ? and deleted_at is null
order by updated_at desc
limit 20;
```

可考虑索引:

```text
(user_id, deleted_at, updated_at, id, title)
```

但把大字段放索引会增加存储和写入成本。不要为了覆盖把长文本放进索引。

## 深分页

问题:

```sql
select * from notes order by updated_at desc limit 20 offset 100000;
```

数据库要跳过大量行。

优化:

- cursor pagination。
- seek method。

例:

```sql
where (updated_at, id) < (:last_updated_at, :last_id)
order by updated_at desc, id desc
limit 20
```

前端列表、评论、session 历史都适合 cursor。

## 排序和临时表

如果 order by 不能利用索引,数据库可能 filesort 或显式 sort。

优化:

- 建匹配 where + order by 的索引。
- 限制返回字段。
- 先取 id 再回表。
- 减少排序数据量。

但不要为了所有排序组合建索引,会拖慢写入。

## Join 慢

Join 慢常见原因:

- join key 无索引。
- 驱动表选择错误。
- 数据量估算错误。
- 返回行爆炸。
- N+1 查询。

优化:

- join key 建索引。
- 过滤条件尽量提前。
- 分页后再 join。
- 预聚合。
- 用 explain analyze 验证。

## RAG 存储相关

note_chunks 查询常见维度:

- user_id / tenant_id。
- note_id。
- chunk_id。
- embedding indexed search。
- lexical search。
- updated_at。

权限过滤必须在检索候选阶段就进入条件,不能等 LLM 最后自己判断。

向量索引和 SQL 索引是不同层次。pgvector ivfflat/hnsw 优化近邻搜索,普通 btree 优化等值/范围过滤。

## 面试追问

问: 慢查询为什么不能只说加索引?

答: 因为慢可能来自全表扫描、排序、join、统计信息、锁等待、返回数据太多或网络传输。加索引也有写入和存储成本。应先看执行计划和实际行数,再按查询模式设计索引。

问: 什么情况下索引会失效?

答: 常见是对索引列做函数、隐式类型转换、like 前置通配、联合索引不满足最左前缀、范围条件后续列无法使用、选择性太差或统计信息不准。

问: 深分页怎么优化?

答: 用 cursor/seek pagination,用上一次结果的排序键作为游标继续查,避免 offset 跳过大量行。排序键要稳定,常用 `(created_at, id)` 或 `(updated_at, id)`。

## Hard negatives

- B-tree 索引不是向量索引。
- 加索引不是免费优化。
- 全表扫描不一定错,小表全扫可能更快。
- cursor pagination 不是 SSE event id。
- Explain 估算计划不等于真实耗时,需要看 analyze 或监控。
